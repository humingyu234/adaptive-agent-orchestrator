# Adaptive Agent Orchestrator

**AAO is a runtime control layer for AI-assisted engineering workflows.**

It lets workers such as Claude Code execute tasks while AAO handles
planning, evidence checks, guardrails, recovery, human review, live
visibility, memory, and audit reports.

## What problem does AAO solve?

AI coding agents are powerful but unreliable.  They can claim a task is
done when it isn't.  They can change files they shouldn't.  They can
retry failures forever.  And the orchestrator can't tell the difference
between real evidence and what the agent just says.

AAO adds **six control dimensions** between the orchestrator and the worker:

| Dimension | What it does |
|---|---|
| **Evidence** | Observed test output and file diffs beat worker claims |
| **Policy** | Protected files, high-risk tools, and required checks are enforced |
| **Recovery** | Every failure has a bounded path — no infinite retry loops |
| **Planning** | Complex tasks get structured plans with risk review before execution |
| **Human Review** | Risky changes pause for human approval, not after-the-fact |
| **Audit** | Honest reports with evidence, failure, and recovery — never fake success |

## Honest Scope

This is a **personal open-source engineering system and proof-of-work
project**, not a claimed production SaaS deployment.

What AAO is:
- A control layer that makes agent workflows more trustworthy
- A proof that evidence, policy, recovery, and audit can be real code,
  not aspirational slides
- A portfolio artifact demonstrating AI-native engineering ability

What AAO is not:
- A production SaaS with uptime guarantees
- A Claude Code replacement
- A generic all-in-one agent framework
- A marketed product with fake users or adoption claims

## Core Pillars

### 1. Workflow Orchestration

AAO decouples agents from workflows so different roles, flows, tools, and
models can be composed, swapped, and reused.

Current capabilities:
- Pluggable agents
- YAML workflow definitions
- Natural-language `ask` entry point
- LLM Router for automatic task routing
- `SupervisorOrchestrator` for top-level coordination
- Per-agent LLM provider and model configuration

Built-in agent roles: `planner`, `search`, `summarizer`, `supervisor`,
`human_review`, `real_search`

### 2. Runtime Evaluation & Control

AAO checks, adjusts, and converges during execution — not just at the end.

Current capabilities:
- `Evaluator L1`: structural checks
- `Evaluator L2`: semantic quality checks
- Retry / fail / continue decisions
- Checkpoint-backed replan
- Supervisor revision
- Rollback
- Max-step convergence control
- Guardrails (input and output)
- Trust hierarchy / tool permissions
- Human Review v2

### 3. Recoverability & Observability

Every run produces structured artifacts for recovery, analysis, and audit.

Auto-generated outputs:
- State persistence
- Checkpoints
- Execution logs
- Convergence report
- Memory bundle
- Failure taxonomy
- Regression compare
- Analyze CLI

## Real Usage (LLM Planning + Claude Code Worker)

```bash
# Full end-to-end: LLM plans, you approve, Claude Code executes
python -m orchestrator ask "Fix the typo in src/utils.py" \
  --planning-mode llm --approve --worker-mode claude-code

# Multi-worker for complex tasks (spawns multiple Claude Code workers)
python -m orchestrator ask "Refactor error handling across modules" \
  --planning-mode llm --approve --worker-mode claude-code --max-workers 2

# Deterministic planning (no API cost) with fake worker (test/inspect)
python -m orchestrator ask "Add unit tests for utils.py" \
  --approve --worker-mode fake

# Plan only — review the plan before deciding to execute
python -m orchestrator plan "Refactor the auth module" \
  --planning-mode llm --approve
```

Requires: `DEEPSEEK_API_KEY` in `.env` for LLM planning; Claude Code
installed and logged in for real worker execution.

## CLI Quick Reference

```bash
# Natural-language task entry
py -m orchestrator ask "Research solid-state battery commercialization"

# Full control chain: LLM planning → approval → worker → evidence → audit
py -m orchestrator ask "<task>" --planning-mode llm --approve --worker-mode claude-code

# Run a workflow file
py -m orchestrator run --workflow workflows/deep_research.yaml --query "your task"

# Single-agent debugging
py -m orchestrator agent --name planner --query "your task"

# Human review
py -m orchestrator review --task-id <task_id> --decision approve
py -m orchestrator review --task-id <task_id> --decision reject

# Runtime analysis
py -m orchestrator analyze list --limit 10
py -m orchestrator analyze show --task-id <task_id>
py -m orchestrator analyze failures --limit 20
py -m orchestrator analyze memory
py -m orchestrator analyze regression --find 10

# Inspect available agents and providers
py -m orchestrator agents --verbose
py -m orchestrator providers --verbose
```

## Multi-Provider Runtime

Supported providers: `mock`, `codex`, `glm`, `kimi`, `deepseek`,
`openai`, `anthropic`, `ollama`

Per-agent provider/model configuration:
```bash
py -m orchestrator run \
  --workflow workflows/deep_research_supervised.yaml \
  --query "your task" \
  --agent-llm planner=codex:gpt-5.4,supervisor=deepseek:deepseek-chat
```

Environment variables via `.env` (excluded from git):
```env
LLM_PROVIDER=deepseek
LLM_DEFAULT_MODEL=deepseek-chat
DEEPSEEK_API_KEY=...
```
